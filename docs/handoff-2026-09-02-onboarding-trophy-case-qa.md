## Findings, in campaign priority order

### 1 · P0 — Username onboarding is dead whenever Top Shot's public API is flaky, and it has been flaky for 3 days
- **Observed:** `POST /api/profile/resolve-and-associate {username}` → 502 for a bogus name, for `jamesdillonbond`, and for any name. Vercel logs: `Top Shot GraphQL failed with 530 … Cloudflare Tunnel error … public-api.nbatopshot.com`. Grouped 72h counts of that error: `/api/wallet-search` 243, `/api/profile/resolve-and-associate` 43, `/api/cron/offers-sweep` 108 — i.e. intermittent for days, not a one-off.
- **Root cause:** `app/api/profile/resolve-and-associate/route.ts:118` calls `resolveTopShotUsername()` (live GQL only). The anonymous home analyzer, `app/api/wallet-search/route.ts:219`, already uses `resolveTopShotUsernameCacheAware()` (4 DB cache layers first, live GQL last) — I confirmed `POST /api/wallet-search {input:"jamesdillonbond"}` resolved fine during the same outage. `wallet_usernames` holds **9,370** cached handles.
- **Why it matters for the campaign:** the username path is the one the hero copy leads with, and it is also the only path that auto-claims a public handle (#2). During an outage every signup silently degrades to the address path, and the error text actively steers them there.
- **Fix (route):** in `resolve-and-associate/route.ts`, import `resolveTopShotUsernameCacheAware` and `supabaseAdmin`, replace the `resolveTopShotUsername(rawUsername)` block with the cache-aware call, and branch on `outcome.found` — `username_not_found_on_topshot` → the existing 404 copy; `topshot_gql_error` / `not_in_any_cache` while GQL is down → the existing 502 copy. Keep the `walletAddress`/`username` assignments identical. Also consider a short retry with backoff on 530 inside `topshotGraphql`.
- **Verify:** `npx tsc --noEmit` clean; signed in, submit a handle that exists in `wallet_usernames` while `public-api.nbatopshot.com` is 530 → 200. **Revert:** `git revert <commit>`.

### 2 · P0 — Address-path users never get a public handle, so they never get a profile URL, share card, or "Your public profile" card
- **Observed:** after adding a wallet by `0x` address, `profile_bio.username` stays NULL; `app/dashboard/DashboardClient.tsx:900` renders `PublicProfileCard` only when `bio?.username` is set (its own comment says "Every collector now HAS one (the handle defaults from their Dapper username)" — true only on the username path). Nothing on the dashboard tells the user to go to `/profile/edit`. DB: 25 users, 23 with a handle, **1 wallet-holder with none** today — small, but this is exactly the population the campaign will create if #1 is not fixed first.
- **Compounding bug:** `app/api/profile/me/route.ts:26-83` derives `username` from `allow_list.username` then `saved_wallets.username` (the *Top Shot* username), never from `profile_bio.username` (the *public handle*). After I set `qa0903`, `/api/profile/me` still returned `username: null`, so `app/profile/[username]/ProfileClient.tsx:301` computed `isOwnProfile=false` and the owner-only "SHARE YOUR COLLECTION / Share on X / Copy link" block (`:487-515`) never rendered on the user's own profile. Anyone who renames their handle in `/profile/edit` loses that block too.
- **Fix (route + client):** (a) in `resolve-and-associate`, when the address path is taken, fall back to the same email-local-part default that `app/api/profile/bio/route.ts:13-16` (`defaultUsernameFromEmail`) already uses, with a collision suffix — or, cheaper and more honest, render a "Claim your public handle" prompt in place of `PublicProfileCard` when `bio.username` is null, linking to `/profile/edit#username`. (b) in `/api/profile/me`, read `profile_bio.username` first and fall through to the existing sources. Grep before changing: `useSessionOwner`, `ProBadge`, and the concierge key on `wallet_addr` from this route, not `username`, so (b) is display-only.
- **Verify:** new address-path user sees a handle prompt or an auto-handle; `/api/profile/me.user.username === profile_bio.username`; share block renders on own `/profile/<u>`. **Revert:** `git revert <commit>`.

### 3 · P0 — "Share on X" on the trophy-case page shares the wrong URL and drops the referral
- **Observed:** on `/profile/qa0903/trophy-case`, "Share on X" opened `twitter.com/intent/tweet?text=My collection on @RipPacksCity. My trophy case is up:&url=…/profile/qa0903?utm_source=share&utm_medium=x` — the **profile** URL (profile OG card), not `/profile/qa0903/trophy-case` (the trophy card the user is looking at). No `&ref=`.
- **Root cause:** `components/profile/ShareProfileButtons.tsx:36-50` `profileUrl()` hard-codes `/profile/<username>`; `app/profile/[username]/trophy-case/TrophyCaseShareClient.tsx:177-181` mounts it without `referrerId` (and without `fmv`/`moments`, which is why the tweet reads "My collection on @RipPacksCity." with no stat).
- **Fix (client):** add an optional `path?: "profile" | "trophy-case"` (or `href`) prop to `ShareProfileButtons`, default `profile`; the trophy page passes `trophy-case` and the viewer's user id when they own it (it already knows `username`; fetch `/api/profile/me` the same way `ProfileClient` does). Tweet copy for the trophy variant: "My trophy case on @RipPacksCity — <n> Moments I chose to show off 👇". Pre-warm the OG on click: `fetch('/api/og/trophy-case/<u>', {mode:'no-cors'})` before `window.open` (cold render measured 3.6–4.7 s; edge-cached afterwards at ~80 ms — X's fetcher is impatient on cold images).
- **Verify:** intent URL contains `/trophy-case` and `ref=`; `curl -sI https://www.rippackscity.com/api/og/trophy-case/qa0903` → `image/png`. **Revert:** `git revert <commit>`.

### 5 · P1 — Pinned trophies cannot be removed on a phone
- `components/TrophySlab.tsx:187-208`: the ✕ is `display: hovered ? "flex" : "none"`, driven by `onMouseEnter`; the whole slab is a `<Link href="/moment/…">`. On touch, the first tap navigates before any hover state exists. Edit Layout mode exposes only ←/→ (verified in DOM: buttons `DONE ← → ← → ← →`), no remove. (Cowork's Chrome would not resize below desktop width this session, so this is a code-verified finding, not a device-verified one.)
- **Fix:** render the ✕ always in `mode==="owner"` (small, low-opacity until hover), and/or add a "Remove" control in Edit Layout mode. **Revert:** `git revert <commit>`.

Moments: 19,380 (dashboard) / 19,381 (profile header + OG) / "19382 moments" (profile collection breakdown). ### 7 · P1 — Trophy pins are entirely client-asserted
- `app/api/profile/trophy/route.ts:46-80` upserts `momentId`, `playerName`, `fmv`, `serialNumber`, `tier`, `thumbnailUrl`… straight from the request body with no ownership check and no server-side lookup; "Enter ID manually" pins any moment on the platform. A campaign that says "show off your case" invites a $1,000,000 LeBron #1/1 on someone's public page within a day. **Fix:** accept `slot` + `momentId` (+ `note`) only, resolve the display fields server-side from `get_moment_detail`/`wallet_moments_cache`, and mark slabs whose moment is not in the user's saved wallets as "not verified in your wallet" on public surfaces (don't block — gifts/friends' moments are a stated use case). **Revert:** `git revert <commit>`.

### 8 · P1 — The funnel never says "trophy case" until slot 1 is on screen
- Landing hero, `/login`, and the "Check your email" panel have no mention of the trophy case; the first-run tour's 5 steps cover collections, wallets, concierge and sniper but not the trophy case; `EmptyHeroState`'s "Pin a moment" copy is unreachable for a zero-wallet user. For a campaign whose CTA *is* the trophy case, add: one landing block ("Build your trophy case" with a real example card like `/api/og/trophy-case/<seed user>`), a one-line value prop on `/login`, and a tour step that points at the trophy case (or replace the sniper step). Copy-only; `app/page.tsx`, `app/login/LoginClient.tsx`, `components/onboarding/FirstRunTour.tsx:38-70`.

### 9 · P2 — Onboarding polish (each small; listed so they can be batched)
- **Raw error slugs reach users.** `app/login/LoginClient.tsx:36-42` shows `auth_failed` / `missing_token` / `session_failed` verbatim and ignores the `description` param the confirm page sets. `DashboardClient.tsx:645,692` throw `data.error`, so a wallet-cap user sees the literal `plan_limit_reached` instead of `data.message`.
- **`/auth/confirm` ignores its `?redirect=`** (`AuthConfirmClient.tsx:106` → `router.replace("/")`); it only works because `/` bounces signed-in users to `/dashboard`. A campaign deep link (`/login?next=/dashboard%23trophy`) is lost.
- **First-run tour:** the device flag `localStorage["rpc:first-run-completed"]` short-circuits before the per-user `/api/profile/first-run-tour` read (`FirstRunTourMount.tsx`), so a second account on the same browser never sees it (that is what happened here); steps don't spotlight their targets (all five rendered as centered modals over a blurred page; no outline/cut-out on the switcher, wallet card, concierge or sniper link they describe); "Save up to 3 wallets free" is hard-coded while the cap comes from `checkFeatureQuota`.
- **Stale localStorage across accounts.** `rpc_owner_key` / `rpc_last_wallet` / `rpc_owned_<addr>` from the previous account survived sign-out expiry; the new user's dashboard ran `[preloader] loaded 15160 owned moments … for 0xbd94cade097e50ac` before any wallet was added. Server side is correctly guarded (`/api/wallet/profile?ownerKey=<other user>` → 403, `saved-wallets?ownerKey=` → own rows only), so this is wasted work + confusing console, not a leak. Clear the `rpc_*` keys on `/auth/confirm` when the user id changes.
- **Display name defaults to the raw email local part** (`TDILLONBOND+QA0903`) until `/profile/edit` is saved; prefer the handle, or "Collector".
- **`/profile/edit`**: page `<title>` is the generic site title; the live "Public URL" preview echoes invalid input (`rippackscity.com/profile/qa 0903!`) instead of sanitizing; load fires `GET /api/profile/bio` 11× (watch the effect deps); the form is long (five league pickers) before the user reaches the X handle — move username + display name + X handle to the top and collapse teams.
- **Picker:** the 🔒 glyph has only a `title="Locked"` — say "Locked on Top Shot"; some entries lack series/league metadata (two Lillard Cosmic serials render differently); search is limited to the top-96 slice and says "No moments match" when the moment simply isn't in that slice (`TrophyPickerModal.tsx:72-81` documents it).
- **Dashboard has two "Load my collection" inputs** on first visit (hero + Saved Wallets section) with different placeholder vocab ("Dapper address, or Top Shot username" vs "Dapper username").
- The "Check your email" panel's envelope icon rendered as a washed-out image at 1568px — worth a look on a retina display.
