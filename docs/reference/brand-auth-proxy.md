## Brand system

- `app/rpc-tokens.css` owns all tokens.
- `var(--rpc-red)` = `#E03A2F`.
- Fonts: `var(--font-display)` = Barlow Condensed, `var(--font-mono)` = Share Tech Mono.
- RULE: never hardcode `#E03A2F` or `'Barlow Condensed'` literals — always use tokens.
- Exception: `ConsoleGreeting.tsx` console `%c` only.
- ⚠ **THERE ARE TWO ACCENT REDS AND THEY ARE NOT INTERCHANGEABLE. Web is `#E03A2F` (`--rpc-red`, and `--por-red` is the SAME value). Email is `#E55A4C`** — rgb(229,90,76), visibly different — and it is hardcoded **on purpose** in email HTML (`lib/emails/**`, `lib/alerts/format.ts`, the alert/subscribe API routes), because **email clients do not support CSS custom properties at all**, so `var(--rpc-red)` there renders as nothing. `__tests__/welcome-email.test.ts` pins it. **So `#E55A4C` is correct in email and wrong on any rendered web surface**, where the token exists.
- ⚠ **The brand guard was structurally blind to the worse half of this until 2026-08-16: `LITERAL` matches `#E03A2F`, i.e. hardcoding the CORRECT red.** Hardcoding the WRONG red passed silently — untokenized *and* off-brand. It shipped on `app/auth/confirm/page.tsx`, the magic-link landing (spinner + message, 3 sites) and on `app/login/page.tsx`, while `login` used `var(--por-red)` for the same role a few lines away. `scripts/check-brand-tokens.mjs` now bans the email accent on web surfaces; it **walks `app/**` + `components/**`** rather than iterating `PROTECTED`, because a guard keyed to a curated list is silent about every file off it. ⚠ **Do not "simplify" it into a blanket ban on the literal** — measured, that fires on all 7 legitimate email uses.
- ⚠ **`--rpc-black` is THEME-AWARE (`#080808` dark, `#FFFFFF` under `[data-theme="light"]`), as is `--rpc-text-primary`.** So a hardcoded dark hex is not merely untokenized, it renders a **black slab in light mode** — the `SupportChat` defect, met again on `/auth/confirm` (`#0a0a0a`/`#fafafa`). The light-mode half is a SEPARATE list in the guard (`NEUTRAL_PROTECTED`) from the brand half (`PROTECTED`); a file can be in one and not the other, so check both before calling a surface clean.
- ⚠ **The auth funnel (`login`, `early-access`, `auth/confirm`) was invisible to the client-page ratchets until the directive detector was fixed** (see the ratchet bullet under Testing), which is why it had never been swept. It is now in `PROTECTED`. Its failed-read handling was checked at the same time and is **CLEAN** — recorded so nobody re-sweeps it: `sendMagicLink` sets `notOnAllowList` only on a precise `403 + reason=not_on_allow_list`, so a network error, a 5xx and a non-JSON body all fall through to a generic "temporarily unavailable" — **an outage cannot tell a real user they are on the waitlist.**

Two files shipped in `public/` were unreachable until 2026-08-13: **`/fonts/*.ttf`** (`ttf` was not an allowlisted extension and the matcher does not exclude `/fonts/`) and **`/llms.txt`** (the AI-crawler sibling of `robots.txt` — the one file whose entire purpose is to be fetched anonymously). The fonts case had teeth: two SERVER-SIDE consumers fetch them over HTTP with no session — the OG profile card (`runtime = "edge"`, so it **cannot** read them off disk) and the trophy-case PDF — and an HTML body passes any `res.ok`/non-empty check, after which satori throws `Unsupported OpenType signature <!DO` **from inside the `ImageResponse` STREAM, after `GET` has returned**, where that route's three-tier try/catch cannot reach it. So the branding never worked in production, and it failed as a **broken unfurl, not a de-branded one**. Fixed with a separate `FONT_ASSET_RX` (`^/fonts/[^/]+\.(ttf|otf|woff2?)$`) plus an exact `/llms.txt` entry, and by validating the BYTES in `lib/og/font-bytes.ts` (`isSupportedFontBuffer`) before they reach any renderer. ⚠ **Directory AND extension, deliberately — do NOT "simplify" this by folding the font extensions into a bare suffix test** (the first version of that fix folded them into the then-live `STATIC_EXT_RX`): such a regex matches any path ending in the extension, which publishes a gated route whose trailing dynamic segment a visitor controls. **That same reasoning is what retired `STATIC_EXT_RX` itself two days later** — the objection was recorded here, applied to the fonts, and not applied to the regex that motivated it. Three durable generalizations: **the response proves the request succeeded, never that a font came back**; **a guard around `new ImageResponse(...)` catches nothing that happens during rendering**, because the body is a stream consumed after the handler returns; and **when adding any new asset type to `public/`, check this allowlist first** — sweep it with `find public -type f | sed 's/.*\.//' | sort -u`. Pinned by `__tests__/proxy-is-public-path.test.ts` (the real font paths and `/llms.txt` public; `/fonts`, `/fonts/list`, `/fonts/a/b.ttf`, `/dashboard/report.ttf` and `/foo/llms.txt` all still gated) and by the HTML-served-at-200 regression case in `api-og-profile-brand-fonts`. ⚠ That test file previously stubbed only a **503** for the font fetch — a shape the old code already handled — which is exactly why it ran green while production was broken: **model the failure that actually happens, not the tidy one**.
**The follows POST/DELETE writers stay fully gated**, and the route gates ITSELF per form — the `?username=` probe reveals only whether the CURRENT viewer follows someone, while the listing form (no query param) still calls `requireUser()` and 401s. ⚠ `isPublicPath` never sees a query string, so BOTH forms bypass the proxy and the route's own guard is what protects the listing — keep that guard when editing the route.

⚠ **OPENING A PATH IN `isPublicPath` DOES NOT MAKE ITS HANDLER READ-ONLY — and a comment asserting that it does is how one survived review for months (P0, fixed 2026-08-15 in `8f59749b`).** `/api/edition-floor` sits on the anon-reachable `PUBLIC_READ_APIS` allowlist under a `proxy.ts` comment reading *"No writes, no user data"*. **That was false**: a caller-controlled `?persist=1` / `{persist:true}` ran a `SUPABASE_SERVICE_ROLE_KEY` **delete-then-insert over today's `fmv_snapshots` rows** for ≤50 editions — an unauthenticated destructive write, latent only because no production caller passed the flag. It is now gated on the operator bearer (`CRON_SECRET` / `INGEST_SECRET_TOKEN`); **an unauthorized caller is not rejected, the flag is simply ignored**, so every existing read caller is unaffected. It was gated rather than deleted because persisting floor data is legitimate work for an authenticated caller — removing the capability is a product call. ⚠ **`check_anon_write_surface()` could NEVER have caught this** — it tests what the anon **DB role** can write, and this route holds the **service-role key**, so the write it enables is invisible to that probe by construction. The guard-scope class again: *ask what a passing probe is structurally silent about.* **When adding or reviewing anything on the public allowlist, read the HANDLER for write paths and caller-controlled flags — the allowlist comment is not evidence.**
