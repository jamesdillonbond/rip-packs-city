The read:

```sql
select count(*) filter (where def ilike '%collection_chains%') as consumers, count(*) as inspected
from (select pg_get_viewdef(c.oid) as def from pg_class c join pg_namespace n on n.oid=c.relnamespace

```

## ⛔ A Solana wallet is not a Flow wallet with different characters (2026-09-19)

**The single most productive defect class on chain two, and every instance was written years before Candy existed.** Flow/EVM addresses are hex, `0x`-prefixed and **case-INsensitive**. A Solana address is **base58, un-prefixed and CASE-SENSITIVE**, and base58 excludes `0`, `O`, `I` and `l`. So the two habits this repo is full of — `.toLowerCase()` and *prepend `0x` if missing* — do not normalise a Solana key, they **destroy** it.

⚠ **THE FAILURE IS SILENT AND IT POINTS THE WRONG WAY.** A mangled key does not error; the read returns **zero rows**, and zero rows render as *"this wallet holds nothing"*. Every instance below looked like an honest empty state.

**Use these, never a bare `.toLowerCase()` or a fresh helper:**

| need | helper (all in [lib/address.ts](../../lib/address.ts)) |
|---|---|
| a stable storage/lookup key | `normalizeAddress()` — folds hex, preserves base58 verbatim |
| "is this an address at all?" | `isSupportedAddress()` / `detectAddressChain()` |
| "is it an address for THIS collection?" | `isValidAddressForChain(value, dbChain)` |
| rendering one to a reader | `displayAddress()` / `truncateAddressForDisplay()` |
| the per-device owner key | `getOwnerKeyForChain()` / `setOwnerKeyForChain()` / `ownerKeyMatchesChain()` in [lib/owner-key.ts](../../lib/owner-key.ts) |

### The instances, and what each one taught

- ⛔ **`resolve_moment_id` had the right query behind a bigint GATE.** The text-keyed `wallet_moments_cache` lookup that resolves a Candy mint was already in the function and already correct — it sat inside `IF v_nft IS NOT NULL`, so every `/moment/<mint>` 404'd. **The data path rarely needs a new arm; the GATE in front of it does.**
- ⛔ **Seven API routes rejected a base58 wallet** via `startsWith("0x")`, a `.toLowerCase()` on the key, or a `contractName` short-circuit. Each returned an empty/500 answer that read as "no data".
- 🚨 **A fix to a route is not a fix to the surface.** `/api/wallet/edition-counts` was repaired and **verified live (0 → 5)** while `MarketClient` still never CALLED it — its effect opened `if (!ownerKey || !ownerKey.startsWith("0x")) return`. **Repair the read, then grep the caller's own gate.**
- 🚨 **`rpc_owner_key` was ONE global localStorage slot.** Dropping its `0x` gate would have OVERWRITTEN a Flow collector's key with a base58 address and blanked every `0x`-gated Flow surface. The slot is chain-scoped now, keyed by `ChainKind` (the EVM chains share one identity), and **Cadence keeps the historical key byte-for-byte**. ⚠ **The sweep that clears it on sign-out / account-switch must be by PREFIX** — `lib/auth/device-keys.ts` listed it by exact name, which left `rpc_owner_key_solana` for the next collector on that browser.
- 🩸 **Fold-and-prefix on a DISPLAYED address is a FABRICATION, not an absence.** Live on `/candy-mlb/player/mike-trout` and `/candy-mlb/edition/mike-trout-pink`: labels read `0x2at8…jrqw` / `0x1bwu…ndix` while the `title=` on the **same element** carried the correct-case mint. ⚠ **The worst instance was an HREF** — `WalletLink` built `/<collection>/collection?wallet=<mangled>`, so every owner link sent the reader to a wallet analyzer that resolved nothing and rendered an **empty wallet**.
- 🧮 **THE QUERY-KEY FACE, and the only one that was never an honest absence.** The `/profile` aggregations built their key with `raw.startsWith("0x") ? raw : "0x" + raw`. ⚠ **These RPCs DO serve Candy** — none of `get_top_movers` / `get_wallet_tier_counts` / `get_cross_collection_portfolio` / `get_wallet_moments_with_fmv` folds its wallet, and they read `wallet_moments_cache` (25,375 Candy rows). Measured: `get_wallet_tier_counts(<base58>)` → `{"COMMON":1626,"LEGENDARY":100}`, `'0x'‖<base58>` → `{}`. **1,726 moments dropped while the wallet still counted as ATTEMPTED.** Use `walletQueryKey` — deliberately NOT `displayAddress`, because a display string folds and **a query key must not change what the database is handed**.
- 📤 **AN OUTBOUND EMAIL is the furthest this class reaches.** `get_cross_collection_portfolio` on a folded base58 wallet returns a structurally COMPLETE object of zeros **that echoes the mangled wallet back**, so it reads as true; `send-digest` gates its portfolio block on `collections?.length`, so a Candy holder's weekly email silently omitted a **$19,386** portfolio.
- ⛔ **AND A HARDCODED MAP BESIDE THE REGISTRY.** `/api/portfolio-export` — the Export CSV control on the Collection tab — carried a four-slug `COLLECTION_UUID_MAP` omitting Candy **and UFC**, so the button answered **400 "Unknown collection"** on two live tabs. Resolve through `getCollection`, gated on `published && pages.includes("collection")`, and **pin that gate**: a bare registry lookup widens to Panini and RWA.
- ⚠ **THE MEASUREMENT TRAP THAT NEARLY CLOSED ALL OF THESE AS "NO DIFFERENCE":** `count(*)` over each variant returned **1, 1, 1**, because these functions return ONE row whose VALUE is the result. **Read the payload.** Likewise `prosrc ILIKE '%lower(%'` said a function folded its wallet — the matching LINES showed the folds were on `player_name` and `tier`.
- 🩸 **THE NAME-RESOLUTION FACE — LIVE ON A PUBLIC BOARD FOR 24 h, AND IT DEFEATED THE HEURISTIC BUILT TO DETECT IT (2026-09-20).** `displayName(addr, names)` folded its argument and then handed the **folded string** to `truncateAddress()` as the fallback, so what `/insights/top-sales` printed as the wallet's identity was an address that resolves nowhere. Measured through the production caller: `buyer_address` `1Ttv9XYVPgHRJQwBX2Ccn5GUcgM5BsAWX13kH4gZEQV` → `buyer_name` `1ttv9xyvpghrjqwbx2ccn5gucgm5bsawx13kh4gzeqv`; six mangled addresses in the first three rows. ⭐ **The second-order defect is the one to remember:** `TopSalesBoardClient` scores a row as having a resolved @handle with `!buyer_name.includes("…")`, and `truncateAddress` returned the folded 43-char string **whole, with no ellipsis** — so a fabricated value passed the very heuristic that exists to catch fabrication. The fix (`1Ttv9X…ZEQV`) repairs the render AND the metric. ⚠ **BOTH TWINS**: `lib/flowty-username.ts` and `lib/analytics/username-resolver.ts` are byte-level copies and only the server one showed the symptom.
- ⛔ **THE WRITE-PATH FACE, AND WHY THE 09-19 SWEEP MISSED IT.** `/api/wallet/save` wrote `walletAddress.trim().toLowerCase()` into `saved_wallets` and handed the same string to `/api/wallet/seed` — destroying the wallet **at the moment of saving it**. `/api/profile/saved-wallets` was fixed 09-19; this is the same write and has **NO IN-REPO CALLER**, which is exactly why it survived: ⭐ **a sweep that follows imports cannot see a route nobody imports.** Route handlers are reachable by URL, not by reference — enumerate `app/api/**/route.ts` directly. (Still LATENT: `saved_wallets` held 135 rows, **0 non-hex**, when this was found.)
- ⚠ **FOLDING BOTH SIDES OF A COMPARISON IS NOT SAFE EITHER.** `walletAlreadySaved` folded the candidate AND every stored row, which looks symmetrical — and makes two DIFFERENT base58 wallets compare equal, so its `true` **BLOCKS a legitimate save**. Same shape in `groupWalletsByAddress` (two Candy wallets merge into one card) and `public-profile`'s distinct-wallet count (undercount). **Symmetry is not correctness when the fold itself is lossy.**
- ⛔ **A CADENCE-ONLY WORKER MUST REFUSE, NOT ANSWER.** `/api/wallet/seed` is four hardcoded Cadence scripts taking `address: Address`. Handed base58 it still RAN, failed all four, and returned **`ok: true` with a row per collection** — counts of 0 a caller reads as a measured empty wallet. It now 400s `unsupported_chain_for_seeder` **with no `results` array at all**, so there is no zero for anything downstream to find. ⭐ **Assert the ABSENCE of the field, not the presence of an error string.**
- ⚠ **`rpc_last_wallet` is NOT chain-scoped, deliberately** — it holds the raw last input, which may be a USERNAME, and a username has no chain. The guard is at the point of USE: a seed belonging to another chain is not auto-searched, and a non-address seed is only searched where a username can be resolved.

### ⛔ The rule that governs every one of these fixes

**NEVER NARROW THE INCUMBENT CHAIN WHILE WIDENING FOR A NEW ONE.** `isValidAddressForChain(key, "flow")` demands exactly 16 hex — **stricter** than the `startsWith("0x")` it looks like a drop-in for. Adopting it on a Flow path is a regression smuggled in under a Solana fix; three component tests caught it on the `0xmine` fixture, and **the fixture was not edited to fit the code**. The same reasoning makes the `|| value.startsWith("0x")` in the search classifier load-bearing rather than redundant. **Pin the hex path as its own no-change arm in every test file that touches these helpers** — without it, the Solana assertions are satisfied by a function that has quietly changed every Flow label in the product.

⚠ **A grep before building found TEN existing truncation helpers.** The canonical pair lives in `lib/address.ts`; only the Candy-reachable call sites were repointed. **Rewriting Flow-only surfaces to fix a Solana bug is how a one-line fix becomes a regression surface.**
