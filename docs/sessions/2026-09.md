### The class: `const { data } = await …` where `not found` is RECORDED, not re-tried

The shape appears **25 times** across `app/`+`lib/`+`workers/`. **Most are harmless**, so a ban is the
wrong instrument. 👉 **The discriminator is not the expression, it is WHERE `not found` LANDS.** In an
enrichment loop a miss costs one un-enriched row and the next tick fixes it. In these seven routes it
landed on:

- **`retry_count + 1`**, and ten bumps RETIRE the row permanently — at `*/15` a sustained read failure
  would have retired every queued row in **two and a half hours**, with no trace but a rising
  `rows_skipped`, which reads as the pipeline working;
- **a cursor that advanced anyway** (`topshot-offers-indexer`) — zero rows written, `ok: true`, and
  nothing revisits a block below the cursor, so the offers are **gone**;
- **a Cadence storm** (`allday-resolve-unmapped`) — `existing` empty ⇒ every edition "missing" ⇒ one
  on-chain call per id, then a mass upsert back over rows already there;
- **a flooded retry queue** (`allday-listings-indexer`), worked with real Cadence borrows and a finite
  budget, for rows that were never unresolvable;
- **`edition_id: null` forever** (`pinnacle-trades-indexer`) — `ignoreDuplicates: true` means no later
  tick corrects it.

**Two siblings found in the same files.** `allday-listings-retry` marked rows `resolved_at` whose v2
upsert had **failed** — the listing is then lost and nothing re-derives it. And all three retry routes
ended their resolved-mark with a log-only error branch followed by `resolved = list.length`; the admin

⭐ **And the exception is now written down.** `wallet-backfill`'s `seeded_wallets` read discards its

**The two corrections, both of my own work, both within the hour**

- **"450,987 recoverable" was wrong by 10×.** It counted rows whose TRANSACTION IS REACHABLE, not rows
  whose SELLER IS DECODABLE — the same circular sizing the fmv-recalc filing described the day before,
  which I had read. It surfaced by watching the **second** tick: the first recovered 109/120 and the next
  six recovered **0 of 720**. Probed: 21 of 21 hash-bucket-sampled studio-history txs are
  `NFTStorefrontV2.ListingAvailable` with zero Withdraw events, against a 3-of-3 positive control. A
  listing moves no NFT. **Reachable 450,987 · decodable ≈ 38,200.**
- **The exclusion that fixed it had the NULL trap.** `NOT IN` yields NULL for a NULL source, so an
  unlabelled row would have been dropped silently — the shape of everything else fixed tonight,
  reintroduced by the fix for one of them. `IS DISTINCT FROM` attempts it instead.

**What I would tell the next session**

- ⭐ **Watch the SECOND tick.** The first tick after a fix is the one most likely to flatter it. Both
  corrections above came from the tick after the one I would have quoted.
- ⭐ **Reachable ≠ convertible.** A floor or a predicate tells you the first; only sampling the
  conversion tells you the second.
- ⭐ **Build a suppression list from the WALK'S OWN OUTPUT.** Mine came from another instrument's
  summary and the post-state caught the function I had skipped.
- ⭐ **A cursored backfill needs a FLOOR, not just a cursor** — a newest-first walk terminates only by
  running out of data.
- ⭐ **`res.ok` is not a liveness check** when the upstream answers 200 for data it cannot serve.
