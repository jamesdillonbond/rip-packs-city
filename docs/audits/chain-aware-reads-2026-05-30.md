# Chain-aware reads audit -- code surfaces (Phase E)

**Created 2026-05-30.** Phase E of the chain-abstraction plan ([handoff](../handoff-2026-05-30-chain-abstraction-phases-cde.md)). A planning artifact -- **no code change**. Classifies every collection-filtering code surface so we know what changes (and what does not) when chain two (Solana / Candy Digital, or possibly Beezie/Base -- see caveats) arrives.

Companion: [chain-aware-reads-db-2026-05-30.md](chain-aware-reads-db-2026-05-30.md) covers the DB-side (functions / views / triggers). This doc is the **code-side** surface (routes, cron, edge functions, lib modules).

Generated from a 9-agent parallel classification workflow over 351 `/api` routes, 28 cron handlers, 11 public routes, 24 edge functions, and the chain-relevant `lib/*` modules. 168 surfaces classified.

## Classifications

- **chain-internal** -- reads collection via `collection_id` FK or registry slug; chain is implicit via the FK. Solana/EVM data flowing through the same query path Just Works. **No change needed** when chain two arrives.
- **assumes-Flow** -- explicitly relies on Flow shapes (Cadence event parsing, FCL/Top Shot/AllDay/Pinnacle GQL fetches, `setID:playID` integer-pair external_id, Flow `0x16`-hex addresses, Flow REST/proxy workers). Stays Flow-scoped **by design**; chain two = parallel `lib/chains/solana/` equivalents, not shared dispatch.
- **needs-chain-dispatch** -- generic enough that it **should branch on chain** when chain two arrives. Annotated `TODO(chain-dispatch)`; the dispatch itself is deferred to chain-two work.

Takeaway: the assumes-Flow surfaces are almost entirely **ingest / indexer / GQL-fetch** edges (one per collection) and **TS-intrinsic product** surfaces (squeeze, pack-EV, rookies, first-mint). These do not need refactoring -- chain two adds parallel Solana ingestors + parallel insight surfaces. The read / serve layer that filters by `collection_id` is overwhelmingly chain-internal and absorbs new-chain rows with zero change. This mirrors the DB-side finding (~75% of collection-aware DB code already reads via the `collection_id` FK).

Two are the new wallet-paste public tools (`squeeze-check`, `tc-report`): they hardcode the Flow address regex `^0x[a-fA-F0-9]{16}$`. At chain two, accept a `?chain=` param (or infer from address format -- Solana base58 vs Flow 0x16-hex vs EVM 0x20-byte) and dispatch to the chain-appropriate RPC. The third is `lib/collections.ts` -- its `marketplaceMomentUrl` / `marketplaceWalletUrl` builders are keyed by slug with hardcoded per-collection templates, so they need a chain-aware URL strategy when a non-Flow marketplace appears. Everything else in the public-insights group is either chain-internal (cohort / profile views) or a TS-intrinsic product surface (assumes-Flow by design).

## Notes on method + caveats

- Classification was done by read-only Explore agents reading the data-access + filter logic of each surface; large files were located, not fully re-read. Spot-check before relying on a single row for a refactor.
- The 351-route total includes many `/api/admin/*` and one-shot backfill routes not individually classified here -- the audit focused on the steady-state read / serve + ingest surfaces per the Phase E handoff scope. Pad this table as new surfaces surface.
- **Parallel EVM data plane (architectural tension).** `lib/evm-rpc.ts` (Flow EVM 747 + Base 8453 read scaffold) and `app/api/cron/evm-transfers-ingest` are already chain-parameterized -- the only pre-existing multi-chain-aware code, and the template for how a generic chain-dispatch surface should look. Per the DB-side audit, this is backed by a separate registry (`evm_chains` / `evm_nft_contracts` / `evm_indexer_cursors` / `evm_nft_transfers`, ~1.01M Base/Beezie transfers indexed since ~May 13), **not** modeled through `collections.chain_type`. So the DB currently has two chain conventions: the `collections.chain_type` enum (Flow data plane) and the `evm_chains.chain_id` registry (EVM raw indexer). Whether Beezie/Base is promoted into the `collections` registry (so the chain-internal analytics functions can see it) or stays a parallel raw-indexer plane is a Trevor decision upstream of the Candy/Solana sequencing. See the DB-side audit + [candy-audit-checklist-2026-05-30.md](../candy-audit-checklist-2026-05-30.md).
- This audit does **not** gate Phase F (drop the `collections.chain` DEFAULT). Phase F only requires `lib/collections.ts` to enforce chain at the type level (Phase C).
