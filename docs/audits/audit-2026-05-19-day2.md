# Audit day 2 — three threads picked up

## Thread 1: `allday-unmapped-resolver` regression — **FIXED**

Overnight, the pipeline dropped from 100% pass to 11% pass. Root cause was a downstream function (`promote_unmapped_sales`) that I hadn't touched yesterday, hitting the 60s ceiling inherited from `resolve_unmapped_sales_for_collection`.

**Diagnosis:** old query used 4 LEFT JOINs across `unmapped_sales × editions(×3) × nft_edition_map` with `WHERE COALESCE(...) IS NOT NULL` post-join. Planner couldn't push `LIMIT 1000` through the post-join filter, so it scanned the entire 458K-row AllDay subset every tick. Only **577 AllDay rows** are actually resolvable (the rest have no `nft_edition_map` entry and no hint), so the query was burning 60s to find a needle.

**Fix:** rewrote with EXISTS subqueries in WHERE (which Postgres pushes down to the base scan) plus correlated subqueries for the actual resolution. Migration `audit_20260519_rewrite_promote_unmapped_sales_exists_pushdown`.

**Verified:** direct call now runs in 17 seconds (was: 60s timeout). First post-deploy invocation drained 614 rows in one shot, archived 187 old resolved rows, refreshed 128 stale FMV entries. Next cron tick (around 14:01 UTC) will confirm production.

## Thread 2: `flowty_archive` growth — **scoped, not fixed**

The table isn't growing because the extractor is slow. It's growing because **most endpoints have no extractor at all** by design.

**The breakdown** of 44,787 unextracted rows:

| Endpoint family | Pending | Has extractor? |
|---|---:|---|
| `collection:{ufc,pinnacle,golazos,allday,topshot}:sale` | **41,692** | No |
| `nft:{topshot,allday,ufc,pinnacle,golazos}` | 2,284 | No |
| `firestore:STOREFRONT_PURCHASED` | 273 | ✅ (keeping up) |
| Probes (royalty / analytics / lending / stats / traits / etc.) | 270 | No |
| `firestore:STOREFRONT_LISTING_*`, `BID_*`, `LOAN_*`, `FUNDING_*` | 25 | No (mostly empty) |

The harvester comment in `app/api/flowty-harvester/route.ts` says exactly this: "preserve LiveToken FMV estimates, aggregated edition stats, fee/royalty info, bid/offer books, and lender offers before Flowty potentially shutters their API. No transformation — we mine the archive in SQL later." So the design is intentional. The growth equation is permanent until you either:

- **(A)** Build extractors for the high-volume endpoints (`collection:*:sale` is ~93% of pending). Per-endpoint pattern would mirror `extract_flowty_purchases`. Significant work — ~5 collections × ~100 LOC each + cron entries + idempotency tests.
- **(B)** Add an unextracted-age prune for endpoints you decide are lower priority. One-line addition to the existing `prune_flowty_archive_api_harvest`: also DELETE rows WHERE `extracted_at IS NULL AND collected_at < cutoff AND endpoint NOT IN (<priority list>)`. Loses some preservation data — your call which endpoints are worth keeping vs. discarding.
- **(C)** Accept the growth and budget for the disk. At current rate (~5K rows/day, ~50 MB/day in this table), you'll add ~1.5 GB/month. The Supabase Pro Micro tier has growable storage, so this is fine for a while if you decide the data is worth more than the storage cost.

No fix auto-applied — this is a product/cost decision I shouldn't make for you. The audit report and this doc record the option set.

**(b) 20 MORE analytics routes** also use `request.url` at build time and emit `Dynamic server usage` errors. Same fix shipped in `d9b5106`: `export const dynamic = 'force-dynamic'` on each.


**(c) SECDEF write-path impersonation vulnerability** — caught during the authenticated-callable SECDEF audit. Three functions accept `p_user_id uuid` but never verified the caller actually IS that user. Migration `audit_20260519_secdef_authn_check_on_write_rpcs` adds `IF auth.uid() IS NOT NULL AND auth.uid() <> p_user_id THEN RAISE EXCEPTION 'forbidden_cross_user'` to:

- `save_fast_break_lineup` — writes lineups + decrements use budget
- `verify_wallet_via_fcl` — marks wallets as verified
- `aggregate_saved_wallet_stats` — writes cached_* fields on saved_wallets

`service_role` callers bypass (auth.uid() = NULL); only blocks authenticated cross-user impersonation. Two read-path functions (`get_trophy_slab_data`, `get_user_top_owned_moments`) also take `p_user_id` but are likely intentional public-profile surfaces — flagged for your judgment, not auto-locked.

**(d) Dependabot config added** at `.github/dependabot.yml` — security-only PRs for npm + weekly GitHub Actions monitoring. Aligns with the CLAUDE.md "no PRs from humans" rule while carving out the CVE exception.

**(e) `lambdaRuntimeStats: {"nodejs":18}` was misread.** The "18" is a *count of lambdas*, not a Node version. Vercel is on Node 24 as configured. No outstanding Node mystery.
