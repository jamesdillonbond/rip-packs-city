- **Confirmed root cause (read-only):** the function ACL is now `{postgres=X/postgres, service_role=X/postgres}` — only `postgres` and `service_role` can EXECUTE (`has_function_privilege('anon',…)`=false). The job runs as `cron_heavy`, which is neither and has no explicit grant. A `REVOKE EXECUTE … FROM PUBLIC` (the 08-01/08-03 client-executable-SECDEF security campaign) stripped `cron_heavy`'s previously-implicit PUBLIC access. Owner=`postgres`.
- **Impact:** the disconnected-ask FMV clamp (a pricing-accuracy guard that clamps FMV against disconnected/stale asks per-collection — normally a healthy 1–2-row daily trickle) no longer runs. Published FMV can drift unclamped against disconnected asks until re-granted. Accuracy-critical given the current accuracy-is-the-gate roadmap.
- **Risk read:** LOW-risk fix, HIGH value. Restoring EXECUTE to an internal pg_cron role does NOT re-widen the anon/authenticated surface.
- **Suggested action (night pass / Trevor):** `GRANT EXECUTE ON FUNCTION public.fmv_clamp_disconnected_ask(uuid, boolean) TO cron_heavy;` then confirm the next 08:55Z tick succeeds. ⚠ **Also sweep for siblings:** the same PUBLIC-revoke could have stripped EXECUTE from other functions called by `cron_heavy`/`cron_light` pg_cron jobs — `check_pgcron_recent_failures()` only surfaces jobs that have already ticked-and-failed since the revoke, so daily/weekly jobs may fail later. Audit `cron.job.command` targets vs `has_function_privilege('cron_heavy', …, 'EXECUTE')`.
