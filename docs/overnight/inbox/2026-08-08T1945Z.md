## ACTION (DONE — see above): index `sales_2026` to kill the perfect-mint-premiums MV refresh scan

**This is the #1 disk-I/O lever on the platform right now** and it's fully diagnosed — the only thing left is a `CREATE INDEX CONCURRENTLY` that must run in a **quiet window with a real psql connection** (a full-partition build; the interactive MCP tooling is 60s-capped and would abort mid-build, leaving an INVALID index on the hot ingest partition — and building during a daytime disk spike just adds I/O to an already-throttled disk). 1 AM is the right time. Do this FIRST among the MV-cluster items.

### Why (measured 2026-08-08)
`rpc-refresh-perfect-mint-premiums` (jobid 236, hourly) burns **~2,417 s/day** refreshing `mv_topshot_perfect_mint_premiums_board` — a **163-row / 128 kB** MV — and fails ~9 of 23 runs at the 600s ceiling. It is the top single source of the intermittent pooler/disk saturation that was 504ing `/api/market`, `/api/sentinel`, price-snapshots, and the entity pages today. The DB is NOT capacity-bound (2 of 90 connections active, CPU idle); it is **disk-I/O bound** (3 backends in `DataFileRead`; 12 GB DB vs 512 MB shared_buffers on the Small tier). Decision recorded with Trevor: **stay on Small, fix the queries** — Medium is the same 2 cores for 4× the cost.

Root cause (from `EXPLAIN` of the MV's defining query): the `ed_med` CTE
```
SELECT edition_id, percentile_cont(0.5) ... , count(*)
FROM sales WHERE collection='nba_top_shot' AND sold_at >= now()-180d AND price_usd > 0.50
GROUP BY edition_id HAVING count(*) >= 15
```
uses `sales_2026_edition_id_price_usd_idx (edition_id, price_usd)` with `Index Cond: price_usd > 0.50`, then **heap-fetches ~406,000 rows just to apply the `collection` + `sold_at` filters** (they aren't in that index). That heap-fetch storm IS the cost. (The `perfect` CTE already rides `idx_sales_2026_pulse_window` fine — leave it.)

### The fix (paste verbatim; SQL editor or a psql session — NOT apply_migration, NOT a txn)
```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_sales_2026_ts_edition_median
ON public.sales_2026 (edition_id, sold_at DESC)
INCLUDE (price_usd)
WHERE collection = 'nba_top_shot' AND price_usd > 0.50;
```
Rationale: partial (TS + price>0.50, matches the query's constant filters → small), keyed `(edition_id, sold_at DESC)` so `ed_med` gets **index-only, pre-sorted-by-edition_id** input (no heap, no sort) with `sold_at` range-filterable and `price_usd` from `INCLUDE`.
