**Source:** `pipeline_runs` (`topshot-wmc-fossil-drain`, 2026-07-20 11:30:40Z, `ok=false`,
`extra={"rpc":"topshot_wmc_fossil_targets","stage":"targets_rpc"}`, `rows_written=0`) ·

Vercel cron `30 11 * * 1`) fired on schedule this Monday and **died at the candidate-selection
stage** with `targets: upstream request timeout`, before doing any work.

Three things make it worth a line rather than a shrug:

1. **It is a third instance of the belief the 07-20 probe falsified.** Its selector
   `topshot_wmc_fossil_targets(p_limit)` carries `statement_timeout=120s` in **proconfig**,
   and the 06-27 ledger entry records that the 120s was added *specifically because* the
   1.58M-row regex scan blows the short default. Claude Code's `438360f` probe proved
   proconfig does not extend the outer ceiling on the PostgREST/`service_role` path either
   — so this job's load-bearing timeout does not bind, and the real ceiling is
   `service_role`'s 30s. Same shape as `get_lock_check_batch` (flagged inert) and
   `get_allday_lock_refresh_wallets` (declined). `remap_topshot_wmc_from_onchain_map()`
   carries `statement_timeout=300s` on the same route and the same reasoning applies.
2. **It is not in `pipeline_cadence_watchlist`**, so `detect_stalled_pipelines()` structurally
   cannot see it. A weekly job gets one attempt and then goes quiet for seven days with
   nothing watching — this failure surfaced only because it happened to land inside the
   `pipeline_runs` retention window.
3. **It is a self-heal, so the failure is silent by construction** — nothing downstream
   complains when a guard stops guarding.

**Severity is honestly LOW, and I want to be clear why:** the thing it guards is currently
**empty**. Measured this tick — TS wmc rows with a UUID-form `edition_key` = **0**. The
06-27 drain cleared all 1,748 and the backlog has not re-accumulated. So this is a broken
guard over a zero backlog, not a live data defect. It matters if fossils return.

**Scope caveat on my own evidence (stated because it changes the claim):** `pipeline_runs`
retains only back to 2026-07-17 18:41Z (daily prune), so 07-20 is the **only Monday in the
window**. I can say this tick failed; I *cannot* say prior Mondays did. Do not read
"1 run all time" off that table as "never succeeded" — I nearly did.

**Suggested action (two parts, neither urgent):**
- Cheap and safe: add a `pipeline_cadence_watchlist` row (weekly cadence ⇒
  `max_silent_minutes` ≈ 10,200, low severity) so the next miss is visible instead of silent.
- The real fix is the ALLDAY-LOCK-REFRESH-SELECTION-COST pattern: make the selection finish
  inside 30s. The regex scan over ~1.6M wmc rows has no supporting index. **Do not propose
  raising the proconfig timeout** — that is the declined pattern, twice over now.

**Risk read:** the watchlist row is additive DB-only and trivially revertible
