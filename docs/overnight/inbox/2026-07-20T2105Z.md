## Item 1 — SALES-INGEST-DUNE resumes UNSUPERVISED on billing-cycle reset (MED, new framing)

**This is the one genuinely new thing this tick found, and it is a framing correction on a
carried item rather than a new failure.**

The ledger frames the Dune 402 as cost/throughput: *"fails safely, cursors parked."* True for
`sales-seller-recovery-dune`. **It is not the whole story for `sales-ingest-dune`, because that
one writes to the partitioned, FMV-feeding `sales` table.**

Measured this tick:

- The pipeline is **not inert** — CLAUDE.md still describes it as never having baked. It went
  live 2026-07-19 20:11Z, ran **5 clean ticks**, and **inserted 1,276 rows into `sales`**
  (`sales_ingest_recovered`: 62,628 rows evaluated, 1,276 `was_insert`, all within a 2h window
  on 07-19). Guards behaved — the audit table exists and is populated, which is the revert path.
- The cursor **advanced**: `sales_ingest_state.cursor_end` walked 2025-12-31 → **2025-09-03**
  (`window_days` 2, floor 2019-01-01). ~4 months of history drained before it stopped.
- It stopped **only** because of the external 402. Today: 11 ticks, 0 ok, 0 inserted.

**The risk:** the datapoint cap is a *billing-cycle* limit, not a config we set. When the cycle
rolls over, the Vercel cron (`11 */2 * * *`) resumes automatically and walks backward toward 2019
at ~2 days per tick — **unattended**, on the `sales` write lane. CLAUDE.md's own activation
instruction was *"watch FMV + eyeball `pipeline_runs.extra` (inserted/skipped_unresolved/
skipped_multimoment) before letting it drain."* That supervision step has not happened; the 402
is currently doing the job of a safety gate by accident, and it will disengage silently.

**Why this matters for the parked-vs-resume decision:** that decision is currently framed as a
cost call with a do-nothing default. The do-nothing default is *"resume unsupervised at an
unknown future date."* That is the part worth making explicit before Trevor chooses.

**Risk read:** MED. Not urgent today (it cannot write while 402'd). Not autonomously shippable —
parking it is a `vercel.json` deploy on the `sales`-write lane **and** a product decision, which
is exactly why the ledger already routed the 402 to an owner call.

**Suggested action (owner, cheap):** pick one before the cycle resets —
1. Park the cron (comment out the `vercel.json` entry) and resume deliberately with a human
   watching the first few ticks; or
2. Leave it armed but do the supervision now — the 1,276 already-inserted rows are auditable
   in `sales_ingest_recovered`, so a spot-check of era/collection/price/edition-resolution on
   those rows would discharge the "eyeball it before letting it drain" step in advance, making
   unsupervised resumption an informed choice rather than a default.

**Revert path for anything already written** (unchanged, from the 07-19 entry):
`DELETE FROM sales s USING sales_ingest_recovered r WHERE r.was_insert AND s.id = r.sale_id;`

**Also worth carrying:** the third Dune consumer, `ownership-sync-dune`, degrades *silently*
under the same cap (1520Z tick: `ok=true`, `exhausted:true`, stale result set re-stamped
`observed_at=now()`, feeding the live Top Owners surface). That one is invisible to every
failure sweep. It strengthens the case for resolving the Dune situation deliberately rather
than waiting it out.
