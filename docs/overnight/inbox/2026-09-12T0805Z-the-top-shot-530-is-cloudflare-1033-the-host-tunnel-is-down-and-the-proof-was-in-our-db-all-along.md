# 🚨 The Top Shot 530 is **Cloudflare error 1033** — the host's own tunnel is down, it is NOT a gated query, and the proof has been in our database since 2026-08-28

**2026-09-12T08:05Z (2026-09-12 01:05 PT) · Claude Code (cloud), autonomous session · instance quiet at measurement.**

Register **#81** has stood open since 2026-09-10 on one question: *is the 530 Top Shot deprecating/gating `searchMarketplaceEditions`, or a transient origin error?* It records the answer as unreachable — *"none doable from the cloud sandbox, whose egress to that host is a hard `CONNECT tunnel failed, response 403`"* — and asks for **one authenticated call from a machine with egress**.

⛔ **No egress was needed. The answer has been stored in `pipeline_runs_daily.last_error` for fifteen days.**

## The measurement

`last_error` holds the **full upstream HTML body**, and every Top Shot 530 in retained history carries the same Cloudflare error page, which explains itself:

> **Cloudflare Tunnel error** — *"You've requested a page on a website (`public-api.nbatopshot.com`) that is on the Cloudflare network. The host (`public-api.nbatopshot.com`) is configured as a Cloudflare Tunnel, and Cloudflare is currently unable to resolve it."*
> `Error reference number: 1033` · `Requested URL: public-api.nbatopshot.com/graphql`

⭐ **`1033` is the ONLY reference number in the entire retained history: 32 pipeline-days, 2026-08-28 → 2026-09-12, no variation.**

```sql
select substring(last_error from 'Error reference number: ([0-9]+)') cf_ref,
       count(*) days, min(day), max(day)
from public.pipeline_runs_daily where last_error ~ 'Error reference number' group by 1;
-- 1033 | 32 | 2026-08-28 | 2026-09-12
```

## What that settles, and what it does not

✅ **It cannot be a per-query deprecation or gate.** 1033 is generated by **Cloudflare's edge before the request reaches the application**. A deprecated or gated GraphQL field answers **HTTP 200 with an `errors[]` body**; a blocked client answers **403 / 1020**. Neither produces a tunnel-resolution failure — and neither would produce the *same* failure for a **different query on a different path**: `getPackListing` on `/marketplace/graphql`, via `backfill-topshot-pack-supply` (jobid 15), 530s too.

✅ **It is not about us.** The error is Cloudflare's own, raised on the way to Top Shot's origin. Our proxy, our IP and our UA are not what is failing.

⛔ **So #81's proposed fix would not have worked.** It suggests *"move the sweep onto a supported query (the proxy already carries unused `topshot-marketplace` / `topshot-browser` routes)"*. **There is no supported query on that host, because the host is not answering at all.**

⚠ **STATED LIMITS — 1033 does not prove everything, and the item should not be over-closed:**
- It does **not** distinguish *"Top Shot decommissioned this host"* from *"Top Shot has a sixteen-day outage nobody has noticed"*. Sixteen days argues decommission; it does not prove it.
- It does **not** prove no OTHER Top Shot host serves this data. **Finding a successor host still needs egress** — that part of #81's ask stands.

## 🚨 WHY NOBODY SAW IT FOR FIFTEEN DAYS — the transferable half

The alert that reports this renders `left(f.last_error, 160)`. Every triage session (including mine, on the first pass tonight) used `left(error, 70..300)`.

⭐ **The body spends its first ~900 characters on a `<style>` block.** `Top Shot GraphQL failed with 530. Response body: <head><title>An error has occured</title><style>body{align-items:center;background:#2d2c32;…` — so **every truncation stopped before the diagnosis**, and the diagnosis was never a fetch away, only a `substring()` away.

⭐ **RULE: when an error column holds an upstream's HTML page, the diagnosis is at the END, not the start. Never triage one with `left(error, N)`** — extract (`substring(error from 'Error reference number: ([0-9]+)')`) or read it whole.

⚠ **And this is the SECOND time in one night that a truncating projection was the defect.** The other was `left(command, 300)` on `cron.job`, which printed a partial gate key into a transcript (tooling-gotchas.md, fourth instance). **A truncating projection is not a faithful projection, in either direction: it leaks what you did not want and hides what you did.**

## ⚠ Separately, found on the way in: the failure-rate alert has an invisible CADENCE FLOOR

`v_pipeline_failure_rates` ends `HAVING sum(runs) >= 5` over a **2-day** window. A **daily** lane produces 2–3 runs in that window and **can never reach 5 — so it is excluded at any failure rate, forever.**

**Measured now:** of **209** lanes with runs in the window, **182 are above the floor and 27 below (13 % of the fleet)**. Of those 27, **two are currently failing above the 25 % threshold and would fire if the floor were not there**:

- `topshot-pack-supply-backfill` — **2/2 = 100 %**, `HTTP 530` (the lane in this filing)
- `match-topshot-players` — 1/2 = 50 %, `rpc_failed: upstream request timeout` (already a register item)

⚠ **The `>= 5` is legitimate in intent** — it stops a 1-of-1 blip paging someone. **But it is expressed in RUNS, which conflates "small sample" with "low cadence".** A daily lane that failed both of the last two days is a *stronger* signal than a 15-minute lane failing 5 of 20 ticks, and only the second one can fire.

**A fix was designed and SIMULATED rather than guessed at.** Admit a low-cadence lane only at a **100 % failure rate across ≥ 2 distinct days** — which is the statistically correct treatment of a small sample, since at n = 2 only 2/2 is signal and 1/2 is a coin flip:

```sql
HAVING (sum(runs) >= 5 AND fail_ratio > 0.25)
    OR (sum(runs) BETWEEN 1 AND 4 AND sum(fail_count) = sum(runs) AND days_all_failed >= 2)
```

**Simulated over the live fleet: 7 lanes fire today, 8 under the proposal, exactly ONE newly admitted** — `topshot-pack-supply-backfill` (2/2, 2 days all-failed). ⭐ **`match-topshot-players` excludes ITSELF at 1/2 = 50 %, so no suppression is needed for it** — which corrects my own first reading of this, written an hour earlier, that named it as the blocker.

⛔ **THE REAL BLOCKER IS SHARPER, AND IT IS WHY THIS IS STILL FILED RATHER THAN SHIPPED.** The single lane the change admits is one whose redness will persist **indefinitely** — Top Shot's host is gone (this filing), so the lane cannot succeed until someone finds a successor or retires it. **That is exactly the #25 permanently-red-instrument condition**, and this estate's own rule for it is: wire it *after* the underlying fix, or *with* an evidenced suppression and a re-check condition. ⚠ **And a pre-emptive suppression here would be worse than useless: it would suppress the ONLY lane the change admits, so the widened arm would fire on nothing and no one could ever prove the new branch works** — a guard that punishes its own success. ⭐ **Two further facts, checked rather than assumed:** `pipeline_alert_suppression` is keyed on `pipeline` ALONE (no `type` column), so suppressing a lane blinds **every** arm for it, not just this one; and `topshot-pack-supply-backfill` is **not** on `pipeline_cadence_watchlist` (verified — the query returns zero rows), so today that particular cost would be nil.

✅ **So the sequence is: settle #81's lane question first (find the successor host, or retire both lanes), then widen this arm** — at which point its one new firing is a lane that can actually be fixed, and the branch is provable.
