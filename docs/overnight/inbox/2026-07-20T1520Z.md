## 1. NEW — DUNE-402 SILENTLY DEGRADES `ownership-sync-dune`, A THIRD (PRODUCT-FACING) CONSUMER, WHILE LOGGING `ok=true`
**Severity: MED-HIGH. Risk to fix: none proposed here — this is a blast-radius correction to a carried item, plus a decision input.**

The carried ledger item **DUNE-DATAPOINT-CAP-402 (MED, nc2)** frames the blast radius as the two sales
walkers only — *"fails safely, cursors parked."* That is incomplete. A third Dune consumer is affected,
and unlike the other two it **does not fail — it succeeds with stale data.**

**Evidence (`pipeline_runs`, 2026-07-20 11:40:27Z, `ownership-sync-dune`, `ok=true`):**
```
{"query_id":"7899011","exhausted":true,"refreshed":false,
 "refresh_note":"execute HTTP 402","offset_reached":114000,
 "incremental_sets":[266,235,224,245,225,257,250,258,218,198]}
```
`refreshed:false` + `refresh_note:"execute HTTP 402"` = it could **not re-execute** the Dune query, so it
paged a **previously-executed (stale) result set** instead and wrote from that.

**Why this is worse than a plain failure:**
- **It logs `ok=true`**, so it appears in no failure sweep, and `detect_stalled_pipelines()` structurally
  cannot see it (it watches for silence, not for stale-but-successful).
- **It writes rows stamped `observed_at = now()`.** Measured live: `topshot_ownership` = 267,742 rows,
  **81,010 written in the last 24h**, newest `observed_at` **1.7h old**. So a freshness check keyed on
  `observed_at` reads *healthy* while the underlying ownership truth is as old as the last successful
  Dune execution. **Freshness-by-timestamp is now decoupled from freshness-of-truth.**
- Consumer is a **live product surface** (Top Owners modules), not a backfill.

This is the repo's documented "looks healthy from every external signal" class (cf. the fmv-recalc
silent stall and the `maxDuration: 900` invisible-ERROR deploys).

**Not quantified here (deliberate):** how far the cached result set has drifted from on-chain truth.
That needs one successful execution to diff against, which the cap currently prevents.

**Decision relevance — this changes the shape of the already-queued owner call.** The ledger frames
"park the two sales crons" as a cost/product question. It is also a **triage** question: the two sales
walkers are backfills that fail loudly and safely; `ownership-sync-dune` is weekly, product-facing, and
degrades silently. Parking the walkers is what frees cycle headroom for the one consumer that has a
live surface and cannot report its own degradation.

**Suggested actions (owner call, none autonomous):**
- (a) Cheapest, independent of the parking decision: make the `exhausted:true && refreshed:false`
  branch log `ok=false` (or write a distinguishable `warn`), so a stale-source run stops reporting clean.
  Today the only way to see this is to read `extra` by hand.
- (b) Sequence the parking decision with the next weekly ownership tick in mind rather than purely as
  a cost call.
- (c) If Top Owners accuracy matters before cycle reset, that surface — not the sales backfills —
  is the one worth spending remaining datapoints on.

**Source:** `pipeline_runs` (`ownership-sync-dune` 11:40:27Z; `sales-ingest-dune` / `sales-seller-recovery-dune`
402 every tick), `topshot_ownership` freshness query. **Carried parent:** ledger line ~44.
