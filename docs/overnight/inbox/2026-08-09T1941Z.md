# Queued — deals/rookies public-board backing views are I/O-bound; prepared fix (apply in a quiet window)

Source: interactive Claude Code session, 2026-08-09 (the PUBLIC-BOARD-CACHING / nc1 thread). Read-only `EXPLAIN` profiling only — **nothing was applied**. This hands a ready, verified fix to whoever owns the MV/index-optimization queue.

## Context
The nc1 snapshot cache (all 5 hot `/insights` boards) is LIVE and working: under the current sustained disk-IO-budget saturation, `deals` and `rookies` have not warmed for ~55 min, yet their pages serve the last-good snapshot (honest, `fetchedAt`-stamped) instead of live-timing-out. So this is **not user-facing breakage** — it is the durable efficiency fix behind the cache, to make those two boards warm reliably again.

`candy-mlb` (125) and `panini-squeeze` (4,472 rows) warm fine in the same ticks where `deals` (37) and `rookies` (61) fail — so it is **per-view cold-I/O cost, not cron contention**. Confirmed by profiling:

- **`rookies`** (`topshot_2025_rookie_index`) — planner cost **~79,595**; **~76k is one node**: the "max mint-#1 sale" trophy lookup does a Nested Loop over ~98 rookie editions × an `Append` across **all 8 `sales_20xx` partitions**, each doing `Index Scan (edition_id, price_usd) … Filter: serial_number = 1`. `sales_2026`/`2027` have `idx_sales_YYYY_serial1` and cost ~15 for that partition; the **historical partitions 2020–2025 lack it** and cost 52–248 each, per edition.
- **`deals`** (`cross_collection_deals_board`) — cost **~20,149**; dominated by ~436 per-edition latest-FMV probes into partitioned `fmv_snapshots` + an 8,449-row `cached_listings_v2` scan.

Both are **I/O-bound, not bad plans** (all index scans) — the same "random probes `shared_buffers` can't hold" class the ledger records for `/api/market`. Precompute/indexing is the lever, not a rewrite.

## Fix 1 (concrete, low-risk) — rookies: replicate the proven serial-1 partial index on the historical partitions
Mirror the exact index the planner already uses efficiently on `sales_2026`:
```sql
-- proven: idx_sales_2026_serial1 = (collection, edition_id, sold_at DESC) WHERE serial_number = 1
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_sales_2020_serial1 ON public.sales_2020 USING btree (collection, edition_id, sold_at DESC) WHERE (serial_number = 1);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_sales_2021_serial1 ON public.sales_2021 USING btree (collection, edition_id, sold_at DESC) WHERE (serial_number = 1);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_sales_2022_serial1 ON public.sales_2022 USING btree (collection, edition_id, sold_at DESC) WHERE (serial_number = 1);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_sales_2023_serial1 ON public.sales_2023 USING btree (collection, edition_id, sold_at DESC) WHERE (serial_number = 1);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_sales_2024_serial1 ON public.sales_2024 USING btree (collection, edition_id, sold_at DESC) WHERE (serial_number = 1);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_sales_2025_serial1 ON public.sales_2025 USING btree (collection, edition_id, sold_at DESC) WHERE (serial_number = 1);
```
Partition sizes (total): 2020 78 MB · 2021 109 MB · 2022 443 MB · 2023 822 MB · 2024 620 MB · 2025 562 MB. A `serial_number=1` partial is a small fraction of each.

### Guardrails (why NOT applied here)
- ⚠ **Must be `CONCURRENTLY`** — historical partitions still take **backfill writes** (`ufc-sales-history-backfill`, `allday-studio-sales-history-backfill` land ~200 historical rows/24h), so a plain build's `ACCESS EXCLUSIVE` lock could block a backfill. `CONCURRENTLY` **cannot run via the Supabase MCP** (not txn-safe; the ~60s tool cap would abort on a hot partition leaving an INVALID index) — run each from the **Supabase SQL editor** (no cap), one at a time, per the 2026-08-08 `idx_sales_2026_ts_edition_median` precedent. Commit a reference migration afterward for repo↔DB parity.
- ⚠ **Do NOT build during a saturation window** — the build itself consumes the depleted disk-IO budget and would worsen the very throttling this is meant to relieve. Wait for `EXPLAIN`-idle / low `DataFileRead` wait. (Measured today: the DB was in a multi-hour saturation spell; even single-view boards warmed ~1/tick.)
- Non-destructive (index only, no data change); revert `DROP INDEX CONCURRENTLY IF EXISTS idx_sales_20xx_serial1;`.
- After building, re-`EXPLAIN` the rookies query to confirm the planner picks the new partial (expect the ~76k node to collapse toward the `sales_2026` cost).

## Fix 2 (design-level, NOT specced here) — deals/market: materialized latest-FMV-per-edition
The `deals`, `/api/market`, and rookies-adjacent FMV lookups all pay per-edition `fmv_snapshots` partition probes because `fmv_current` is a **VIEW**, not an MV. A materialized `fmv_current` (latest snapshot per edition, refreshed on cron) would replace the LATERAL/Append probes with one indexed read. This is the standing `/api/market` precompute item — a hot-FMV-path design decision, needs the pricing owner, not an autonomous ship.

## Do NOT
- Bump `statement_timeout` (documented anti-fix for this cluster).
- Upgrade the compute tier (disk-IO-bound, not compute-bound — Medium is the same 2 cores).
- Change the cron to sequential warming — the evidence (panini 4,472 rows succeeding while deals' 37 fails in the same tick) shows it's per-view cold I/O, not contention.
