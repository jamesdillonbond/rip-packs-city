## Disposition — 2026-11-02 ~11:22 PM PT (Claude Code cloud): NOT a leak, NOT a prune failure — a TOAST high-water mark; no change

Split the size by relation instead of reading the total: **heap 10 MB** (7,002 rows, oldest row exactly at `pg_net.ttl` = 6 h, so the TTL prune is keeping up) · indexes 176 kB · **TOAST `pg_toast.pg_toast_51873` 2,571 MB holding only 504 MB of LIVE response bodies**. Pruned rows free TOAST space for REUSE inside the file; plain vacuum does not return it to the OS, so the file keeps its largest-ever size and grows only when the 6-hour live window of response bodies grows (several lanes moved to 5-minute cadences on 11-02). The "sawtooth" figures in focus.md therefore track the live window, not a leak. **Levers, deliberately not pulled:** `VACUUM FULL` / pg_repack would reclaim ~2 GB but takes an ACCESS EXCLUSIVE lock on a table the pg_net worker writes every second; lowering `pg_net.ttl` would shrink the live window but several drains join responses by request id minutes to hours after dispatch. **Falsifier for a real problem:** heap rows older than the TTL, or live content (`sum(pg_column_size(content))`) climbing past ~1 GB.
