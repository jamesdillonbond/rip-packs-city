## The shape

| | Top Shot | All Day |

⭐ **Both select on the very thing they then write.** Once the last candidate is filled the pool is empty by construction, and from that moment **every tick reports "no candidates" and succeeds** — which is exactly what a finished, healthy drain looks like. There is no error, no timeout, no `ok:false`, and no row that says "this data is old". The lane is not broken; it is *done*, permanently, and nothing distinguishes done-forever from done-for-now.

⚠ **THE ALL DAY CASE WAS ALREADY DIAGNOSED IN WRITING, INCLUDING THE PREDICTION THAT IT WOULD RECUR.** Migration `20260901071258`'s header says: *"Its candidate query is `allday_pack_supply.select('dist_id').is('opened_count', null)` — i.e. it selects on the very column it then fills. The hydrator will freeze again the moment it finishes."* **It has.** 3,020 of 3,195 rows are back to 2026-06-30, and the 175 it repaired are frozen at 2026-09-01.

## Why #74 read it as a dead lane, and why that matters

#74 concluded the Top Shot freeze was the **upstream** dying (`newest successful fetch 2026-08-26 — two days before the host died`), tying it to **#81**'s Top Shot GraphQL 530. ⛔ **That inference does not hold, and it has a practical consequence: fixing #81's 530 would NOT unfreeze the 2,083 rows.** They are not waiting on the upstream; they are not in the candidate set at all.

⭐ **The two facts are both true and the causal link between them is the error.** The lane really does 530 — but only on the **2 dists that have never succeeded** (`8125`, `8327`, `supply_err='HTTP 530'`, `total_minted` NULL on both). Those two are the *entire* live candidate set. So the 530 explains why the pool never empties completely; it explains nothing about the 2,083.

⭐ **The tell that separates them, and it was free:** `max(updated_at)` over the table is **2026-09-11 08:15Z** while `max(updated_at) WHERE supply_ok` is **2026-08-26**. A sixteen-day gap between "newest row" and "newest GOOD row" says the lane is still running and still failing on a small tail — not that it stopped.

## ⛔ What is NOT shipped, and the order is the finding

**The candidate predicates are unrepaired ON PURPOSE.** Shipping the Top Shot one today makes the page **worse**:

- with the upstream 530ing, a re-walk flips all 2,083 rows to `supply_ok = false`;
- the failure branch does not clear the counters, so `pack_distributions` keeps serving the same numbers;
- so the page would show the **identical stale figure** while **losing the age it just gained**.

⭐ `last_success_at` is precisely what removes that trap — a re-walk that 530s now degrades to *"as of 76d ago"* rather than to silence. **So the order is: the column (done) → the predicate → and the predicate only once #81's 530 clears.** The All Day half additionally needs an edge-function redeploy, which `20260901071258` records as blocked on a hardcoded gate literal.

## ⭐ PROMOTE — the transferable rule

**A candidate predicate that selects on the column it fills is a ONE-SHOT, not a refresher — and once it finishes it is indistinguishable from a healthy drain, because every later tick honestly reports "nothing to do" and succeeds.** The symptom is never an error; it is a `*_updated_at` column with an implausibly small number of DISTINCT values. ⭐ **That is the cheap detector and it needs no new instrument:** `count(DISTINCT updated_at::date)` on any hydrated table. Top Shot read 28 across 75 days; All Day read **2**. A refresher cannot produce a 2.

⚠ **And a second-order lesson about this register.** The All Day diagnosis was correct, complete, and written down — **in a migration header**, where the next author never looks. CLAUDE.md already says a comment is only read by someone already in that file. The same sentence applied to Top Shot eleven days later and nobody connected them, because nothing indexed the *shape*. **When a filing names a transferable defect class, the class belongs in `docs/reference/`, not only in the migration that fixed one instance of it.**
