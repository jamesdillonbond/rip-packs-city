## 1. NEW (LOW/MED) — `ALLDAY-LOCK-REFRESH-WALLET-FETCH-TIMEOUT`: candidate-selection fn is missing the `statement_timeout` its own sibling was given yesterday

**Source:** `pipeline_runs` `allday-lock-refresh` (6 fails/24h) · `pg_proc.proconfig` ·
`app/api/cron/allday-lock-refresh-batch/route.ts` (Vercel cron `23 * * * *`, shipped 07-19).

**Signature.** Failing ticks die at `stage: wallet_fetch` with
`wallet fetch: canceling statement due to statement timeout` — i.e. inside the SECDEF
candidate-selection RPC `get_allday_lock_refresh_wallets(p_limit)`, before any Cadence work.
Failing ticks 07-20 **13:23Z** and **16:23Z**; 4 more on 07-19 (18/19/20/22Z). 6 of ~24 ticks.

**The gap is exact and precedented:**

| function | proconfig |
|---|---|
| `get_lock_check_batch` | `search_path=public, pg_temp`, **`statement_timeout=120s`** |
| `get_allday_lock_refresh_wallets` | `search_path=public` — **no statement_timeout** |

`get_lock_check_batch` was given 120s on 07-20 (`audit_20260720_get_lock_check_batch_statement_timeout_120s`)
for *precisely* this failure mode: the candidate **selection** read — not the Cadence leg — hitting the
service-role timeout and silently delivering 0 rows. The All Day scheduler shipped the day before with
the same shape and never got the same treatment.

**⚠ Do not apply this blind — last night's own lesson bears on it.** The 07-20 night pass
(`audit_20260720_mv_refresh_crons_to_cron_heavy`) *falsified* the belief that function `proconfig`
re-arms `statement_timeout`, and CLAUDE.md now records that. That finding was on the **pg_cron** path;
this route is a **Vercel cron → PostgREST** call, which is the same path where `get_lock_check_batch`'s
120s was reported as effective. So the precedent probably holds here — but given the belief was wrong
once this week, the fix wants a **measured** confirmation (fire the RPC and observe it survive past
the current ceiling), not an assumption.

**Severity is LOW/MED, and I am correcting my own first read.** I initially read
`wallets_processed` 60 → 59 → 8 as degrading throughput. Over the full 24h that is **wrong**:
partial ticks are scattered (33 @04Z, 43 @01Z, 45 @21Z, 8 @17Z) against a 60/60 norm, and *every*
tick — pass or partial — runs 234–277s against the route's 270s soft deadline. Partial ticks are the
deadline binding on whale-heavy batches, which is by design, not decay.

**The pipeline is in fact working.** All Day `lock_checked_at` coverage is **284,258 / 333,699 = 85.2%**
(0/333k on 07-19), and `lock_flips` decays exactly like a converging first pass:
2111 → 1646 → 1397 → 1247 → 1130 → 928 → 69 → 24 → 16 → 5. So this is throughput drag on a drain
that is nearly finished, not a break.

**Why it is still worth fixing:** CLAUDE.md gates un-suppressing the All Day lock display
(`PortfolioSummary` "Locked FMV" tile + `CollectionMomentTable` "Held/Locked", currently rendering "—")
on this coverage catching up. Every lost tick is ~60 wallets of delay on a queued user-facing
un-suppression. Cheap, bounded, and it removes a stale-lock display honesty problem.

**Suggested action:** mirror the sibling —
`ALTER FUNCTION public.get_allday_lock_refresh_wallets(integer) SET statement_timeout='120s';`
then confirm on the next `23 * * * *` tick that `stage: wallet_fetch` failures stop.
**Revert:** `ALTER FUNCTION public.get_allday_lock_refresh_wallets(integer) RESET statement_timeout;`
**Target metric:** `allday-lock-refresh` `wallet_fetch` fails → 0/24h; AllDay `lock_checked_at`
coverage → ~100%, then the display un-suppression becomes a verified fast-follow.
