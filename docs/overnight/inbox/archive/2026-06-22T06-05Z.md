**Root cause — the 200s fn timeout is impotent on the pg_cron path:**
- The fn `refresh_topshot_special_serial_owners_mv` DOES carry `statement_timeout=200s` in proconfig (confirmed via pg_proc) — but the run died at exactly **120s**, i.e. the **session/role default** statement_timeout, NOT 200s.
- Mechanism: `statement_timeout` is armed ONCE at the start of the top-level command (`SELECT refresh_...()`), using the GUC value at that instant (the ~120s default). A function-local `SET statement_timeout` (proconfig, applied at function ENTRY = mid-command) updates the GUC but does **not** re-arm the already-scheduled timeout for the in-flight command. So the proconfig 200s never governs the REFRESH. This is exactly why moving off the API-gateway 120s cap didn't help — the DB session has its own 120s ceiling here.
