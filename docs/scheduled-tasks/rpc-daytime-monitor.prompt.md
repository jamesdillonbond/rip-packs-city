## 1c. Spell-time discipline — during a saturation spell, file SYMPTOMS, not CAUSES (added 2026-08-17 after a round-trip that shipped a refuted headline)
Before drawing ANY causal conclusion, take the positive control: `SELECT count(*) FILTER (WHERE wait_event_type='IO') AS io_wait, count(*) FILTER (WHERE state='active') AS active FROM pg_stat_activity WHERE pid <> pg_backend_pid();` — if a majority of active sessions are in IO wait (or `rpc_ops_snapshot()` / a plain indexed `count(*)` times out), you are IN a spell. Then:
- **File what you observe as a SYMPTOM; do NOT assert a cause, a cost figure, or any "cheap/expensive" judgment.** Every duration read during a spell is uninterpretable — your own probe adds IO to what it measures, and run-to-run the query hits different instances. The lesson, paid for: the one fix that survives a spell is the one NOT derived from it. STOP probing into a building spell rather than pushing on.
- **Defer every causal claim to a quiet-window re-measure**, and say so verbatim in the filing ("symptom observed under saturation — re-measure in a quiet window before acting"). Flag for re-measure; do not conclude.
- A durations characterization needs a **≥several-day distribution, never an 8-run tail** (an 8-run tail read "11–18s, uncontended-cheap" on a job that is 116.8s avg / 480s max / ~5.4 h-per-week over 7 days).
- **A denied admin function is NOT a denied capability.** `cron.alter_job` returning `permission denied` does not mean "pg_cron can't be rescheduled from here" — `cron.schedule` under `SET LOCAL ROLE <owner>` is a different, working path. File the specific block, never generalize one function to a whole capability. (You still don't reschedule — that's the night pass/Trevor — but hand off the correct capability, not a false wall.)
- **A CONSTANT structure cannot be a spell's cause.** The heavy-cron band is the same jobs at the same minutes every hour, yet a job's overlap swings with its own runtime — so the pileup is a consequence of long runtimes, not their cause. Don't file a constant as the cause of a swinging effect.
- **A LIMIT that never binds is a full sweep.** Tell: a wide runtime spread (e.g. 11s↔966s) with no failure-rate signal, on a query carrying a `LIMIT`. Verify by `EXPLAIN` row-estimate vs the LIMIT (a `rows=1` estimate that emits ~382k means the LIMIT is cosmetic) — the acceptance test for any proposed fix is `EXPLAIN` showing the LIMIT can bind, NOT a fast wall-clock.
